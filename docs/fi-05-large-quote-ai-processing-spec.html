FI-005 — Large Quote & Invoice AI Processing
Fix the parsing failure on large multi-page supplier quotes & invoices (50+ line items). Two compounding causes: Heroku's 30-second router timeout and a too-small max_tokens ceiling truncating Claude's JSON. Dev-team handover spec.

Section 01
Symptom
Larger supplier PDFs (typically 6+ pages or 50+ line items) fail to parse. The page silently drops to demo data, or shows a misleading API-key error. Small documents (1–3 pages, <30 lines) still parse fine — which is why it looked intermittent.
User-visible messages observed:
• "Parse warning: Could not parse Claude response as JSON — using demo items"
• "ANTHROPIC_API_KEY not configured"  (misleading — the key is fine)
Reference failing file: 8-page Terex Australia quotation, 65 line items, 132 KB PDF (quote #1840277195-0, subtotal $29,794.72 ex-GST, $32,774.22 inc-GST). This is the canonical regression case — any fix must parse it end-to-end.
Section 02
Root cause — two compounding issues
The feature "had been working" because the team's test files were small. Two independent ceilings are both hit only on large documents, and they stack: even after fixing one, the other still bites.
1
Heroku H12 router timeout — 30s initial-response budget
Vision parses of multi-page PDFs routinely take 30–90s. Heroku's router kills any request that hasn't sent its first byte within 30 seconds (H12 Request timeout) — well before our handler finishes awaiting Claude. The client receives a 503, and the frontend's catch-all branch mislabels it as an API-key failure. On the Terex file this fired at ~30s.
2
max_tokens: 4096 truncates Claude's JSON mid-stream
A 65-line invoice serialized as pretty-printed JSON is ~4,500–5,000 output tokens. Claude runs out of output budget partway through and the response ends mid-key (the Heroku log showed it cutting off literally at "gst… on line 43). JSON.parse then fails → server logs Claude returned non-JSON → demo fallback.
Why it looked like "it used to work": both ceilings only trip on large docs. Small test invoices return in <15s under 4k tokens, so they sailed through. The bug is purely a function of document size.
Section 03
The fix — five server-side changes
All changes are in server.js and apply identically to the three parse endpoints: /api/parse-invoice, /api/parse-statement, /api/parse-quote. No data-schema changes.
① Heartbeat-stream the response Backend
Defeats H12. Commit the HTTP status immediately on request receipt, then write one whitespace byte every 10s while awaiting Anthropic. This swaps the 30s "no initial response" timer for Heroku's lenient 55s "no bytes between writes" timer, which each heartbeat resets. 
function startHeartbeat(res) {
  res.status(200);
  res.setHeader('Content-Type', 'application/json');
  res.write(' ');                          // commits status + headers
  const tick = setInterval(() => res.write(' '), 10_000);
  return { end(payload) { clearInterval(tick); res.end(JSON.stringify(payload)); } };
}
Consequence: once the heartbeat starts, the HTTP status is locked at 200, so structured errors (rate-limit, insufficient credits, model overloaded) can no longer be signalled by status code — they must come back in the JSON body, e.g. { code:'RATE_LIMITED', friendly:'…', docsUrl:'…' }. A leading whitespace byte before the JSON is harmless — JSON.parse ignores leading whitespace.
② Bump max_tokens 4096 → 16384 Backend
Across all three parse endpoints. Sonnet-4-5 supports up to 64k output tokens; 16k is the balance between headroom (fits ~200 line items) and cost. This alone fixes the Terex file.
③ Force minified JSON in the prompt (~40% more headroom) Backend
Prepend to every parse prompt. Claude was emitting pretty-printed JSON, which roughly doubled the token cost per line.
OUTPUT FORMAT (CRITICAL): Reply with a single line of MINIFIED JSON.
No code fences, no preamble, no commentary, no markdown, no trailing notes.
Do NOT pretty-print — no newlines, no indentation.
Just the raw JSON object starting with { and ending with }.
④ Robust JSON extractor with truncation recovery Backend
Replace the naive JSON.parse with a four-strategy extractor tried in order:
1
Direct JSON.parse (happy path).
2
Strip ``` / ```json fences and retry.
3
Balanced-brace scan from the first { (handles preamble/trailing prose), ignoring braces inside string literals.
4
Truncation recovery — walk the brace stack; find the innermost open scope that has a comma boundary (a guaranteed-safe cut point at a value edge); slice there; close every still-open scope in reverse order. Annotate truncated:true so the caller knows it's partial. A 200-line invoice that hits the ceiling still returns ~180 usable lines instead of nothing.
⑤ Defensive file-type detection Backend
Browsers (especially macOS Safari/Finder) sometimes send application/octet-stream or an empty MIME type. Accept the file if either the MIME type or the filename extension matches PDF/image. 
const PDF_EXT   = /\.pdf$/i;
const IMAGE_EXT = /\.(png|jpe?g|gif|webp)$/i;
const isPdf   = file.mimetype === 'application/pdf' || PDF_EXT.test(file.originalname);
const isImage = file.mimetype?.startsWith('image/')  || IMAGE_EXT.test(file.originalname);
Section 04
Client-side change — minimal
Because AI errors now arrive inside a 200 response (see ①), every parse caller must check for data.code after the response.ok check and before assuming success. Applies to BillImportPage.tsx, BillDetailPage.tsx, StatementImportPage.tsx. 
// inside .then(async response => { const data = await response.json(); ... })
if (data.code) {
  setAiFailure(data);   // surface friendly banner — do NOT fall back to demo
  return;
}
if (data.truncated) {
  // optional: show "some lines may be missing" notice; data is still usable
}
Section 05
Acceptance criteria
The fix is done when all four pass against the deployed endpoint.
TestExpected
POST /api/parse-invoice with the 8-page / 65-line Terex quote HTTP 200, <90s, lines.length === 65, subtotalExGst === 29794.72, totalIncGst === 32774.22, truncated === false
Same endpoint, synthetic 150-line invoice lines.length >= 100, truncated either false or true — never demo data
Anthropic returns a rate-limit / credits error HTTP 200, body { code, friendly, docsUrl }, client shows the friendly banner (not "API key not configured")
Upload PDF with application/octet-stream MIME (Safari/macOS) Accepted — not rejected as "Only PDF or image files supported"
