FI-024 — FieldInsight MCP Server: Conversational Experience
Layer the AI assistant experience on top of FI-022's MCP server. Defines the conversational use cases, full tool catalogue, proactive nudge rules, job data shape, and 4-phase rollout that lets a user (Ceri) query, schedule, optimise, and analyse her field-service operation through natural language with Claude / Alfred / any MCP-aware client.

1 · Why
Make FieldInsight conversationally accessible
FieldInsight already holds the data that matters: jobs, techs, run orders, line items, status history. The opportunity is to make that data conversationally accessible and proactively useful through an MCP server, so the AI can:
  • ✓Nudge the user about upcoming conflicts before they become problems.
  • ✓Answer ad-hoc business questions ("what's the revenue on Tuesday's run?").
  • ✓Act on the user's behalf — reschedule jobs, reorder a run, suggest assignments.
  • ✓Analyse historical patterns (job durations, staffing efficiency year-on-year).
Strategic: FieldInsight would be an early MCP adopter (a "guinea pig") — a chance to shape how field-service tools integrate with AI assistants while the standard is still hardening.
Relationship to FI-022: FI-022 ships the MCP infrastructure (OAuth, token store, typed API client, generic CRUD tool layer). FI-024 ships the MCP experience (the specific conversational tools, nudges, and data shapes Ceri-style users need). FI-022 must land before FI-024 can begin.
2 · Example User Experiences
What it feels like in conversation
Four representative interactions. Each one is unblocked by a different combination of read, write, and nudge tools defined later in this spec.
2.1 — Proactive nudge: public holiday conflict
AI Hi Ceri — it's Thursday. Next Monday is a public holiday (Labour Day, VIC) and you currently have 7 jobs booked across 3 techs that day. Would you like help rescheduling them?
User "Yes, move them all to Tuesday" — or — "Show me which ones".
2.2 — Run order optimisation · Phase 4 (future)
User Here's tomorrow's run for Jake — can you assess it?
AI Looks like jobs 3 and 4 backtrack across the same suburb you visited in job 1. Reordering to 1 → 4 → 3 → 2 → 5 saves ~22km and ~35 min of drive time. Want me to apply it?
Note: Walk-order / run-order optimisation isn't a v1 use case. v1 default sort is by job type (Service → Install → Quote → Callback). The run_order_position field stays accessible & editable for manual overrides, but FieldInsight isn't yet using sequenced run-order in production. Route optimisation (this example) lands in Phase 4 once drive-time data and route metrics are exposed.
2.3 — Business questions on the fly
User What's the value of this run?
AI Tuesday's run for Jake totals $4,820 across 6 jobs (4 service, 2 install). Three jobs are quote-only and not included.
2.4 — Analytics
User What's the average time Jake spends per service job?
AI Over the last 90 days, Jake's median on-site time for "Service" jobs is 1h 12m, based on status-change timestamps (Arrived → Completed).
User Compare staff for this site vs last year.
AI Last year you ran this site with 10 techs over 6 weeks. This year you're projected to do it with 8 techs over 4 weeks — the team is more senior (avg. tenure 2.3 yrs vs 0.9 yrs last year), and average job duration is down 18%.

4 · MCP Tools
The conversational tool catalogue
The server exposes these tools. Tool names are illustrative — final names land during implementation. Each tool maps cleanly to one or more FieldInsight API endpoints (per FI-022's typed client).
4.1 Read — Jobs & Runs
list_jobs
Filter by date range, tech, status, type, customer, region.
get_job
Full detail for one job including line items, status history, attachments.
get_run
Sequence of jobs for a tech on a date. v1 default sort: by job type (Service → Install → Quote → Callback). If run_order_position is set on a job, it overrides the type-based order. Walk/run-order optimisation is on the roadmap (Phase 4) but not the v1 default.
get_run_metrics
Drive time, distance, total $ value, slack time for a run.
list_job_history
Past jobs for analytics, with status-change timestamps.
search_jobs
Free-text search across descriptions, customers, notes.
4.2 Read — People & Calendar
list_techs
Active techs, skills, regions, current capacity.
get_tech_availability
Leave, working hours, current load over date range.
list_public_holidays
By region, forward-looking.
list_notification_rules
Configured nudge rules (see Section 3).
get_pending_nudges
Active triggers awaiting user attention.
4.3 Write — Actions
reschedule_job
Move a job to a new date/time (and optionally tech).
reorder_run
Set a manual sequence for a tech's day by writing run_order_position on each job. Field stays editable for ad-hoc overrides; not the v1 default — primary v1 ordering is by job type.
reassign_job
Change the tech on a job.
bulk_reschedule
Move N jobs at once (e.g. "move Monday's jobs to Tuesday").
update_notification_rule
Create / edit / disable a rule.
Safety contract: All write tools require explicit user confirmation in the AI flow — the AI proposes, the user approves before the tool fires. See Open Question 5 for the auto-apply opt-in discussion.
5 · Job Data Shape
Minimum fields the MCP server must expose per job
status_history is the critical field — it's what makes "average time per job" answerable. Each status change must carry a timestamp (Booked → Dispatched → Arrived → Completed, etc.). 
Job
├── id
├── date, start_time, end_time, duration
├── type (Service / Install / Quote / Callback / ...)
├── description
├── status + status_history[]   ← timestamps power duration analytics
├── customer { id, name, address, region }
├── techs[]                     ← can be multi-tech
├── units                       ← e.g. number of items / sqm / hrs
├── amount                      ← total $ value
├── line_items[] { description, qty, unit_price, total }
├── run_order_position          ← editable manual override; NOT the v1 default sort
├── notes, attachments
└── flags { conflicts_with_holiday, on_sla_risk, ... }
Why status_history matters: "Median on-site time" = median(Completed.ts − Arrived.ts) across N jobs. Without timestamped status changes, none of the analytics in Example 2.4 are answerable. Confirm with FieldInsight that every status change writes a timestamped row.
v1 ordering decision (2026-05-12): The default sort within a tech's day is by job type (Service → Install → Quote → Callback → other). FieldInsight isn't yet using sequenced walk/run-order in production, so we deliberately keep the surface simple in v1: jobs of the same type cluster together so Ceri can batch-think. The run_order_position field remains exposed and editable via reorder_run for ad-hoc manual overrides — when set, it wins over the type-based order. Once route metrics (drive time, distance) land in Phase 4, walk-order optimisation becomes a primary use case and this default may flip.

How the AI translates speech into tool calls
For each canonical user question, the orchestration the AI would perform.
User questionTools the AI would call
"What's on Monday and is anything clashing?"list_jobs(date=Mon) · list_public_holidays · get_pending_nudges
"Reschedule Monday's jobs to Tuesday."list_jobs(date=Mon) → bulk_reschedule
"What's on for Jake tomorrow, in the order he'll do them?"get_run(tech=jake, date=tomorrow) — returned sorted by job type (v1 default), with any run_order_position overrides honoured

"Average time Jake spends per service job?"list_job_history(tech=jake, type=Service, last=90d) then compute from status_history
"Show me jobs conflicting with public holidays in the next month."list_public_holidays · list_jobs(date_range)
"Compare staffing this year vs last year on Site X."list_job_history(site=X, year=last) + same for this year
7 · Open Questions
Decisions blocking implementation
Each of these needs an answer before the corresponding tools land.
  • Q1 · Walk plans — deferred (not v1)
    Originally: is "walk plan" a distinct entity (multi-day route across a site) or another view of a run? Resolved for v1 (2026-05-12): walk-order / run-sequence is not a primary use case yet — FieldInsight isn't using sequenced walk-order in production. v1 sorts by job type; the run_order_position field stays editable for manual overrides via reorder_run. Revisit (and design get_walk_plan) in Phase 4 when route metrics are exposed.
  • Q2 · Job history depthHow far back should analytics queries reach? 12 months? All-time? Affects performance and pagination design (and informs how aggressively we cache).
  • Q3 · Skill / seniority dataFor the year-on-year staffing comparison to work, we need tech tenure and skill ratings exposed. Are these already in FieldInsight or do they need to be added?
  • Q4 · Multi-tenant authOAuth per user, scoped to their FieldInsight account. Confirm token model — likely inherited from FI-022's encrypted token store.
  • Q5 · Write-action safetyShould writes always go through a confirmation step, or can the user opt in to "auto-apply low-risk changes"? If yes, what counts as low-risk (single reschedule? bulk < N? same-tech reorder?).
  • Q6 · Real-time vs polled nudgesDoes the MCP server push notifications, or does the AI poll get_pending_nudges on each session? MCP standard is request-response; push needs a separate webhook or daemon.
8 · Suggested Phasing
Four phases, each independently shippable
Phase 1 unblocks 60% of the value (read-only Q&A). Phases 2–4 layer in actions, proactivity, and optimisation.
1
Read-only MVP
Unlocks revenue questions, run inspection, basic analytics, conflict surfacing. Most value per day of build effort.
  • ✓list_jobs · get_job · get_run
  • ✓list_techs · list_public_holidays
  • ✓list_job_history
2
Actions
Unlocks "yes, move them" follow-throughs. Now the AI can both answer and act.
  • ✓reschedule_job
  • ✓reorder_run — manual override of the v1 type-based sort; auto-optimisation lands in Phase 4
  • ✓reassign_job
  • ✓bulk_reschedule
3
Proactive nudges
Unlocks the "Hi Ceri, Monday's a public holiday…" experience. AI starts the conversation instead of waiting to be asked.
  • ✓list_notification_rules
  • ✓get_pending_nudges
  • ✓update_notification_rule
4
Optimisation — walk-order becomes primary here
Drive-time and distance maths land here, plus route-optimisation suggestions ("save 22km by reordering"). This is where the v1 default sort (by job type) is reconsidered and walk-order optimisation can become the default once metrics back it up.
  • ✓get_run_metrics with drive-time / distance
  • ✓Route optimisation suggestions (proposal layer over reorder_run)
  • ✓Optional get_walk_plan (see Q1) if multi-day site walks turn out to be a distinct entity
  • ✓Re-evaluate v1 default sort: should walk-order beat job-type once metrics exist?
9 · Success Criteria
How we know FI-024 is working
Concrete, verifiable. Each maps to one or more phases above.
SC-1
Ceri can ask "what's on next week and is anything clashing?" and get a useful answer in one turn.
SC-2
The AI can propose and (with approval) execute a bulk reschedule in under a minute.
SC-3
Status-history-based analytics ("avg duration per tech per job type") return correct numbers verified against the FieldInsight UI.
SC-4
The proactive nudge for a public holiday fires reliably at the configured lead time.
